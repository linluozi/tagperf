# tagperf

**Cross-release performance archaeology for Python projects.** Point it at a git
repository and a tiny workload; it measures every release tag in an isolated
process, finds step changes, bisects a step to a single commit, and then proves
causality by reverse-applying that commit and re-measuring.

This repository is a **measurement tool plus the evidence it produced**. We did
not modify click. The case study asks a question that a single benchmark cannot
answer: *when did click's argument parsing get 1.86x faster, and which commit
did it?*

Upstream: none

## Headline result (click, 15 release tags, 3 workloads)

| finding | measured |
| --- | --- |
| parse a 10-option command, 8.1.6 → 8.1.8 | **263.7 → 141.8 µs (1.86x faster)** |
| the same step on 2000 positionals, 8.1.6 → 8.1.8 | 1264.9 → 1131.7 µs (1.12x faster) |
| the same step on help rendering, 8.1.6 → 8.1.8 | 467.9 → 354.0 µs (1.32x faster) |
| commits between 8.1.6 and 8.1.8 | 47, localised in **6 measured builds** |
| culprit | `70c673d` *Fix eagerness of help option generated by `help_option_names` (#2811)* |
| revert proof | reverse-applying `70c673d` returns to **266.3 µs vs 264.5 µs baseline (+0.68%)** |
| A/A null control on the same tree | arm B / arm A = **0.9912 (0.88% deviation, stable)** |

The 1.86x step is not a benchmark artifact: the parsed parameter dict is
byte-identical before and after (same JSON for 8.1.6, 8.1.8 and 8.5.1), and the
reverse-applied commit reproduces the old cost within 0.68%.

## What tagperf does

```
tagperf run      -> trajectory: every tag, R independent processes per tag
tagperf analyze  -> adjacent-release ratios + bootstrap CI + changepoints
tagperf control  -> A/A null control (two arms on the same tree, alternating)
tagperf bisect   -> direction-aware binary search over first-parent commits
tagperf revert   -> reverse-apply the culprit, re-measure, compare to baseline
```

Design rules that the code enforces:

- **One process per repeat.** Repeats are fresh interpreters, so allocator
  state and import caches never leak between samples. The reported value is the
  median of per-run medians, never the fastest run.
- **A fixed classifier.** The bisect threshold is the geometric midpoint of the
  two endpoint medians, computed *before* the search; no measurement taken
  during the search can move the goalposts.
- **Direction-aware.** The same search localises speed-ups (`m <= midpoint`) and
  slowdowns (`m >= midpoint`). A one-directional bisect silently returns the
  first commit when handed an improvement; that bug is why this flag exists.
- **Self-verification is mandatory.** A bisect result carries
  `previous_is_good` and `culprit_is_bad`. If the culprit does not re-measure on
  the wrong side of the midpoint, the result is reported as unverified — see the
  negative result below.
- **Verification-driven escalation.** When a result fails its own verification,
  `bisect` re-runs the whole search with a doubled repeat budget and reports both
  attempts in `attempts`, instead of returning the unverified answer.

## Usage

```bash
# 1. measure a release trajectory (oldest first)
tagperf run --repo ../click --workload workloads/click_wide.py \
  --tags 8.1.6,8.1.8 --iters 120 --repeats 5 --out out.json

# 2. find adjacent-release step changes
tagperf analyze --input out.json --min-ratio 1.10 --out analysis.json

# 3. A/A control (must be stable before trusting a verdict)
tagperf control --repo ../click --tag 8.1.6 \
  --workload workloads/click_wide.py --iters 120 --pairs 5 --out aa.json

# 4. localise a step, then prove it causally
tagperf bisect --repo ../click --good 8.1.6 --bad 8.1.8 \
  --workload workloads/click_wide.py --iters 120 --repeats 5 --out bisect.json
tagperf revert --repo ../click --commit 70c673d37eb91ba42a129be9037caf3ebed62f3e \
  --workload workloads/click_wide.py --iters 120 --repeats 7 \
  --baseline-us 264.477 --tolerance 0.02 --out revert.json
```

A workload is a Python file with `setup()` returning a zero-argument callable
(and optional `NAME` / `WARMUP`). `tagperf` inserts the checked-out tag's `src/`
at the front of `sys.path` before importing it, so `import click` resolves to
that tag — not to site-packages.

## Bisect and revert evidence (`evidence/click/`)

`bisect-wide-8.1.6-8.1.8.json`:

- 47 first-parent commits, **6 measured builds** (upper bound `ceil(log2(47)) + 1 = 7`).
- Steps: `3ec3ac51` 259.3 good, `9aeb586c` 264.0 good, `fdc6b020` 140.6 bad,
  `70c673d3` 139.7 bad, `26aa7bf3` 263.8 good, `273fb901` 270.2 good.
- Verdict: previous commit `26aa7bf3` = 264.5 µs (good), culprit `70c673d` =
  138.6 µs (bad). `previous_is_good=true`, `culprit_is_bad=true`.
- The culprit is a merge-free commit, so the reverse diff is unambiguous.

`revert-wide-70c673d.json`: 7 process-level repeats after `git apply -R` of the
227-line culprit diff give **266.3 µs** against the 8.1.6 baseline of
**264.5 µs** — ratio **1.0068**, inside the 2% tolerance, `ok=true`.

`aa-wide-8.1.6.json`: five alternating pairs on the *same* tree, ratio
**0.9912**, deviation **0.88%** (`stable=true`). The A/A gate must pass before
any step verdict is read; it did.

## Negative result: the help drift is not localisable

The help workload rises from 363.8 µs (8.3.3) to 421.7 µs (8.5.0) in the
trajectory, i.e. +15.9% over 76 commits. `bisect-help-8.3.3-8.5.0.json` ran 7
builds and proposed `c3535905`, but on re-measurement the culprit came out at
373.4 µs against a midpoint of 377.1 µs — **`culprit_is_bad=false`**. The step
is not a single-commit step; we publish the failed localisation rather than a
regression claim. The two endpoints themselves moved between sessions
(390.5 µs vs 421.7 µs for 8.5.0), which is why 5 repeats are a screening budget,
not a verdict.

```bash
python3 -m venv .venv && .venv/bin/pip install -e . && .venv/bin/pip install pytest
.venv/bin/python -m pytest tests -q
```

Then run the `tagperf run` / `analyze` / `control` / `bisect` / `revert` commands
above with `--repo /tmp/click`. The evidence files were produced with
`--iters 120` (wide, help), `--iters 12` (many), `--repeats 5`, one workload at a
time, on an otherwise idle machine.

## Tests

`7 passed in 21.1s` (`python -m pytest tests -q`). Coverage:

- changepoint detection, flat/noise rejection, deterministic bootstrap CI;
- an end-to-end synthetic git repository with 8 commits: the bisect must find the
  one injected slowdown commit, then the revert must restore the baseline within
  tolerance;
- the same fixture in reverse: a commit that *removes* the cost must be found with
  `direction=speedup`, which is the regression test for the one-directional
  classifier bug described above;
- both bisects assert `attempts[-1].verified is True`, so an unverified answer
  fails the suite rather than being reported.

Two defects were found by this suite and fixed: the fixture originally shadowed
the worker-selected tree with the repository root (bisect therefore measured one
tree for every commit), and the 20-iteration fixture ran in ~1.5 ms per process,
where a single scheduler hiccup could break the revert assertion. The fixture now
imports only from the worker-selected tree and uses 200 iterations per process;
12 consecutive full-suite runs passed.

## Limitations

- Absolute µs values are machine-specific; only ratios are portable.
- 5 process-level repeats per tag is a screening budget. A/A control bounds the
  session drift, but a 5% effect is not resolvable at this budget.
- The bisect walks first-parent history and refuses revert proof on merge
  commits; a regression introduced inside a merge branch is located to the
  merge, not to the inner commit.
- No memory or CPU-time measurement yet: the tool reports wall-clock per
  operation, nothing else.
- Workloads are microbenchmarks of click's parser/help paths, not a production
  CLI. They are equal-work across versions (parsed params and help text hashes
  were checked), but they do not cover I/O, shell completion or prompting.

## 本轮创新

首次把「发布版本轴」做成可判定的因果闭环：逐 tag 隔离进程重放 → A/A 空跑把关
→ 方向感知的分段 bisect → 对命中 commit 做同树 reverse-apply 复证。与已有的
sametree/pr-evidence（复核已开 PR）和 wheel-src-delta（wheel↔tag 字节比对）
不同，这里回答的是「哪一次提交改变了成本」，并用撤回后回到基线 ±2% 来证明，
而不是再解释一个已开 PR。实测把 click 8.1.8 的 1.86x 解析加速定位到单个
commit `70c673d`，撤回后回到 264.5 µs 基线的 +0.68%；同时对 help 的 +15.9%
漂移给出了「无法定位到单 commit」的反例，避免把噪声写成回归。
